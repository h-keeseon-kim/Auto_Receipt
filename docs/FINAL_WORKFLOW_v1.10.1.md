# ReceiptHub v1.10.1 最終運用フロー

## 管理者のアップロード済み領収書確認

「提出履歴」のアップロード済み領収書は、各領収書を次のいずれか1つへ分類します。

```text
再提出判断待ち
確認が必要
AI未確認
AI処理中
AI確認済み
管理者確認済み
ファイルなし
```

管理者はステータスタブを選択し、対応対象だけを表示できます。AI処理中は、処理が完了した領収書から別ステータスへ移動し、タブ件数と表示中一覧をリアルタイム更新します。

一覧は横方向の情報量を減らし、長い横スクロールをなくすため、次の4列です。

```text
利用者 / 領収書月
サービス / ファイル
確認状況
操作
```

提出状態、保存状態、アップロード日時は関連セル内の補足情報として表示します。AIチェックリスト、払先、利用者名、カード番号、AI・管理者メモは「確認内容・AI抽出情報を表示」から展開します。狭い画面では表をカード表示へ切り替えます。

- **再提出判断待ち**: AIが明確な不一致候補を検出し、管理者の最終判断が必要
- **確認が必要**: AIが曖昧または確認不能とした項目が残っている
- **AI未確認**: AI検査未実行
- **AI処理中**: AI待機中または抽出中
- **AI確認済み**: カード末尾を除く必須確認項目がチェック済み
- **管理者確認済み**: 管理者が領収書本体を確認して確定済み
- **ファイルなし**: 保存期限切れまたは削除済み


## 領収書の追加入力と月切り替え

同じサービスへ領収書を追加するときは、既存の領収書レコードを更新せず、新しいレコードとして追記します。同じ元ファイル名を使用した場合も、内部保存パスはUUIDで分離されるため、先に登録したファイルは保持されます。

複数ファイル対応のアップロード欄では、1件ずつファイルを選択またはドロップしても、すでに選択したファイル一覧へ追加します。選択をやり直す場合は「選択をクリア」を使用します。既存領収書の行にある操作は「既存ファイルを差し替え」であり、新規追加とは明確に分けて表示します。

ユーザーの領収書発行月セレクターと、管理者の提出月・明細月セレクターは、月を変更した時点で自動的に対象月へ移動します。「表示」ボタンは使用しません。

## Pカード利用設定の位置づけ

Pカード利用有無はサービスマスター共通の属性ではなく、**ユーザーごとの利用サービス**に保存します。同じサービスでも、利用者ごとにPカード支払いか、それ以外の支払いかを分けて管理できます。

```text
ユーザーA / ChatGPT（サブスク） / Pカード利用
ユーザーB / ChatGPT（サブスク） / Pカード未使用
```

Pカード利用サービスだけが、次の対象になります。

- 領収書アップロード
- 月次の必須提出・API利用確認
- 4日・10日のリマインドメール
- 全社ご利用代金明細との照合

Pカード未使用サービスは利用中サービスとして一覧に残りますが、領収書提出は不要です。 その月にPカード利用サービスも「その他」の領収書もない場合、月次ステータスは「提出不要」と表示します。

## 一般ユーザーのサービス登録

サービスマスターにあるサービスを「サービス利用登録」から追加する際、初期値は選択されていないため、次のどちらかを必ず明示的に選択します。

```text
Pカード利用
Pカード未使用
```

サービスマスターにない新規サービスを例外申請する場合も、サービス名、支払い方法、用途に加えてPカード利用有無を必須入力します。管理者が承認すると、その設定を対象ユーザーの利用サービスへ引き継ぎます。

## Pカード設定の後日変更

一般ユーザーは「利用サービス」の各行にある「Pカード設定」から、自分のサービス設定を変更できます。管理者は「利用サービス管理」→「ユーザー別サービス状況」→「編集」から変更できます。

```text
Pカード利用 → Pカード未使用
```

- 以後の領収書提出対象から除外
- リマインド判定から除外
- 全社Pカード明細のサービス候補から除外
- 開いている再提出依頼は対応済みに変更
- 過去の領収書ファイルと提出履歴は保持

```text
Pカード未使用 → Pカード利用
```

- 領収書提出・API利用確認の対象へ追加
- 未対応の場合はリマインド判定の対象
- 全社Pカード明細の照合候補へ追加

## 月次提出

月次サマリーはPカード利用サービスだけを提出対象として集計します。

```text
必須提出（サブスク等）
利用時提出（API等）
対応済みサービス数
未対応サービス数
```

Pカード未使用サービスは、別に「提出不要」として件数とサービス名を表示します。領収書アップロードのサービス選択肢にも表示しません。

従量課金 / APIの「この月は利用なし」申告も、Pカード利用サービスだけで利用できます。

## リマインドメール

リマインド対象は、利用中の一般ユーザーのうち、Pカード利用サービスに未提出・未確認項目があるユーザーだけです。

- 通常リマインダー：Pカード利用中の必須提出サービスに未提出がある場合
- 重要リマインダー：上記に加え、Pカード利用中のAPIサービスに利用確認待ちがある場合
- Pカード未使用サービスだけを利用しているユーザー：送信しない
- Pカード利用サービスの対応がすべて完了しているユーザー：送信しない

## 全社ご利用代金明細照合

全社ご利用代金明細はPカードの利用履歴であるため、候補サービスはPカード利用として登録されているユーザーサービスだけに限定します。

照合候補となる通常領収書は、アップロード時のPカード利用スナップショットが有効なものだけです。「その他」の追加領収書は、明細内容との一致候補として引き続き評価します。

サービスを後からPカード未使用へ変更しても、過去にPカード利用中としてアップロードした領収書の監査情報は保持します。

## 管理者画面

「利用サービス管理」→「ユーザー別サービス状況」で、次を確認できます。

- 利用中サービス数
- Pカード利用サービス数
- Pカード未使用サービス数
- 各サービスのPカード状態
- 登録元・停止元・最終領収書月
- Pカード設定を含むサービス編集

管理者の月次提出状況には、Pカード利用サービス数とPカード未使用・提出不要サービス数を分けて表示します。

## 再提出依頼とメール通知

「アップロード済み領収書」の再提出依頼ボタンは、対象領収書の「AIでファイル名を修正・検査」が完了した時点で有効になります。AI未確認・AI待機中・AI抽出中の領収書では無効のままです。URLを直接送信した場合も、AI検査未完了なら処理を拒否します。

管理者が再提出依頼を実行すると、次を一連の処理として行います。

```text
対象領収書と実ファイルを提出項目から削除
提出済み月を「未提出領収書あり」へ戻す
再提出依頼管理へ登録
ユーザー画面へ再提出通知を表示
ユーザーの登録メールアドレスへ再提出依頼メールを送信
```

メールには、対象領収書月、対象サービス、対象ファイル、管理者が入力した理由またはAI・チェック結果から補完した理由、再アップロード画面URLを記載します。送信結果は「メール送信」のログへ「再提出依頼」種別で保存します。

停止中ユーザーには既存のメール抑止方針を適用し、メールを送信せずアプリ内の再提出依頼だけを登録します。メールアドレス未登録またはSMTP送信失敗の場合も、再提出依頼そのものは取り消しません。管理者画面で送信結果を案内します。

マイグレーション：

```text
receipts.0026_email_resubmission_request
```

このマイグレーションはメール送信ログの種別へ「再提出依頼」を追加します。既存の領収書、再提出依頼、メールログは削除しません。

## 既存データの移行

マイグレーション：

```text
receipts.0025_p_card_usage
```

移行時の初期値：

- 既存の全ユーザーサービス：Pカード利用
- 既存の全領収書スナップショット：Pカード利用
- 既存の例外申請：Pカード利用

既存の提出履歴、領収書ファイル、AI判定、再提出依頼、ご利用代金明細の解析結果は削除しません。

## サービスマスターからの利用ユーザー確認

管理者の「利用サービス管理」→「サービスマスター」では、各サービスの「利用中ユーザー」を展開すると、現在そのサービスを利用中のユーザー名とPカード利用状態を確認できます。

```text
OpenAI API（従量課金 / API）
├ user-a@example.com / Pカード利用
└ user-b@example.com / Pカード未使用
```

ユーザー名を選択すると「ユーザー別サービス状況」タブへ移動し、そのユーザーの全サービスを確認・編集できます。停止済みサービスの利用者は「利用中ユーザー」には含めず、従来の「割当合計」には履歴として含めます。利用者が多い場合は一覧内を縦スクロールします。

## ボタンラベルの表示ルール

日本語のボタン文字は途中で分割しません。画面幅が狭い場合は「サービス利用登 / 録」のように文字だけを折り返さず、ボタン全体を次の行へ移動します。この共通ルールを、通常ボタン、表内操作、ナビゲーション、管理タブ、ステータスバッジへ適用します。

## v1.10.0 UI修正

- 管理者の「アップロード済み領収書」で、選択中ステータス名と「を表示中」を同じ表示単位にまとめます。件数だけを右側に配置し、文言が画面中央へ分離しないようにします。
- 「AIでファイル名を修正・検査」は、実際のAI処理中だけ `aria-busy=true` と待機カーソルを使用します。処理対象がないため無効な場合は通常の無効カーソルを表示します。
- AI処理完了後は、処理対象件数に応じて実行可能または無効へ戻し、処理中の文言を残しません。

## v1.10.0 ご利用代金明細の照合判定

照合は合計点だけで決定せず、次の順序を固定します。

```text
必須条件ゲート
↓
候補の優先順位
↓
同じ優先順位内だけ補助スコアで順位付け
↓
明細側・領収書側の一対一性確認
```

明確な対象月不一致、金額・通貨不一致、サービス・払先不一致、利用者名不一致は除外条件です。これらは点数が高くても曖昧候補へ入りません。領収書のカード末尾はv1.10.1以降この除外条件に含めず、記載がある場合だけ補助証拠として扱います。情報がないことと、明確に異なることは区別します。請求名義をサービスへ結び付けられず「不明」であっても、金額・通貨が完全かつ一意で、ほかの必須条件に矛盾がなければ提出済み候補として扱い、管理者確認対象にします。

管理者画面では、各候補について必須条件判定、優先順位、除外理由、順位付け根拠を確認できます。

## v1.10.1 カード末尾の扱い

領収書にカード末尾が印字されないサービスがあるため、**領収書のカード末尾一致は必須条件ではありません**。

```text
領収書に末尾7210の記載あり
→ 同じ候補区分内の補助スコア +40点

カード末尾の記載なし・読取不可
→ 0点の中立
→ 候補除外なし、減点なし、自動照合停止なし

7210以外の末尾が明記
→ 必須条件不一致としては除外しない
→ 自動確定だけを止め、管理者確認候補として保持
```

照合の優先順位や候補区分は、対象月、金額・通貨、サービス・払先、利用者名などの必須条件で先に決定します。カード末尾の+40点が、下位候補を上位候補へ昇格させたり、明確な不一致を覆したりすることはありません。

領収書のAIファイル名作成でも同じ考え方を使います。カード末尾が印字されていなくても、払先・名称・日付・金額・通貨・サービス関連が確認できればファイル名を生成します。管理者確認チェックでもカード末尾は任意で、未記載だけでは手動確認件数に含めません。明確に別番号が記載されている場合だけ、管理者の再提出判断候補として残します。

なお、**アップロードされたご利用代金明細書そのもの**のカード末尾7210確認は別の検証です。対象Pカードの明細書であることを確認するため、明細書単位では従来どおりカード末尾を必須確認します。

既存の解析済み明細には再照合マーカーを付与し、明細PDFをOpenAIへ再送信せず、保存済みの明細行と領収書を新ルールで一度だけ再照合します。

旧ルールでカード末尾の未記載だけを理由にAI確認が保留されていた未確定領収書は、管理者が次回のAI実行ボタンで再検査できる未確認状態へ戻します。デプロイ時にOpenAI APIを自動実行することはありません。
