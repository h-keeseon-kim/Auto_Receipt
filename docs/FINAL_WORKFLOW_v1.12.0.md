# ReceiptHub v1.12.0 最終運用フロー

## ご利用代金明細照合の目的

ご利用代金明細照合では、カード明細の各行について、対応する領収書が提出されているかだけを確認します。

```text
必要な結果
├ 一致：対応する提出証拠がある
├ 解析要確認：関連する提出ファイルはあるが必要情報を解析できない
├ 未一致：対応する提出証拠がない
└ 対象外：管理者が領収書不要と判断した
```

誰が利用した請求なのかは推定しません。管理画面・照合結果PDFにも利用者候補やサービス所有者候補を表示しません。

## 照合ルール

v1.12.0では、実際の2026年7月分全社明細61行と提出PDF63件を全件監査し、単純な「1 PDF = 1領収書」照合を廃止しました。

```text
直接一致                       56件
返金書内に記録された元決済       1件
明示的に紐付く返金の相殺          1件
同一請求元内の近接返金相殺        1件
未一致                         2件
```

詳細仕様は `docs/MATCHING_RULES_v1.12.0.md` を参照してください。基本順序は次です。

```text
PDF本文から取引構成要素を抽出
↓
Invoice / Receipt / Transaction IDで重複排除
↓
金額・通貨完全一致、請求元一致、利用日±1日の直接一致を全体一対一割当
↓
返金書類内の元決済を確認
↓
明示的に紐付く返金を相殺
↓
同一請求元内の近接返金相殺
```

利用者は照合条件に含めません。ファイル名も証拠に使いません。

### 取引構成要素

1つのPDFに元決済と返金の両方が記載される場合、それぞれ別の構成要素として保存します。照合目的は「対応する提出PDFがあるか」の確認なので、本文から請求元・取引日・金額・通貨を確認できるInvoiceも提出証拠として扱います。支払済み領収書と請求書が同じInvoice番号を持つ場合は1取引として重複排除し、支払済み領収書を優先します。金額・日付・払先が同じだけでは重複扱いにしません。

### 解析要確認

提出ファイルはあるものの、取引日・金額・通貨・払先を抽出できない場合は、未提出ではなく「解析要確認」にします。対応する提出ファイルを確認できない場合だけ「未一致」にします。

## 管理者画面

各明細行をカード形式で表示します。

```text
明細番号・利用日・ご利用先・金額
照合状態
対応する提出ファイル・返金計算
判定メモ
管理者操作
```

照合候補一覧、候補スコア、優先順位、曖昧候補、候補からの手動確定は表示しません。

### 色

- 一致：通常または緑系
- 解析要確認：黄色
- 未一致：赤色
- 対象外：グレー

未一致は、取引構成要素の直接一致・重複排除・返金相殺を実行しても、対応する提出証拠を確認できないことを意味します。解析できない提出ファイルが関連する場合は「解析要確認」として分離します。

### 管理者操作

```text
領収書対象外にする
領収書対象に戻す
最新の領収書と再照合
```

新しい領収書のアップロード後に「最新の領収書と再照合」を実行すると、保存済み明細行と領収書だけを再照合します。明細PDFをOpenAIへ再送信しません。

## 照合結果PDF

PDFには次を掲載します。

- 明細月と対象領収書月
- 明細書基本情報
- 未一致・解析要確認行一覧
- 全明細照合結果
- 対応領収書ファイル名

利用者候補は掲載しません。未一致行は赤色、解析要確認行は黄色でハイライトし、返金相殺では使用したファイルと計算内訳を掲載します。

## API利用なし申告

利用者を推定して申告を取り消しません。明細行へ実際に領収書が一致し、その領収書が登録サービスに紐づいている場合だけ、該当ユーザーの「対象領収書月は利用なし」申告を取り消します。

## 既存データ移行

マイグレーション：

```text
receipts.0032_empirical_statement_reconciliation
```

実施内容：

- 領収書へ金融書類区分、取引参照番号、関連参照番号、取引構成要素を追加
- 明細行と複数の領収書構成要素を結ぶ照合証拠テーブルを追加
- 既存領収書を本文再確認可能な状態へ戻す（マイグレーション中のOpenAI呼び出しなし）
- 既存解析済み明細へ再照合マーカーを追加
- 次回の明細ページ表示時に保存済み明細行と最新の提出PDFを新ルールで再照合
- 明細PDFのOpenAI再解析は行わない
