# ReceiptHub v1.16.2 最終運用フロー

## 1. 領収書の解析

1. PDFから元決済・返金・Payment historyを金融イベント構成要素として抽出する。
2. 物理ファイルのSHA-256を保存する。
3. Invoice番号、Transaction ID、関連ID、またはSHA-256と金融署名から安定フィンガープリントを生成する。
4. 同一Invoiceや同一PDFの重複構成要素を、支払済み証拠優先で重複排除する。

## 2. 照合候補の収集

1. 選択明細月だけでなく、明細行に含まれる実利用月を収集する。
2. 前月末決済、後日返金、返品元確認に必要な領収書を候補へ含める。
3. 過去明細と管理者確定明細が`consume`済みのフィンガープリントを取得する。
4. 先行所有者・管理者所有者の構成要素を自動候補から除外する。
5. 後続の自動所有者は、先行明細が必要とした場合だけ計算グループ単位で解放できる候補として保持する。

## 3. 現在明細の再照合

1. CardStatementを`select_for_update`でロックする。
2. 同じ明細の旧自動証拠を削除し、管理者確定証拠を維持する。
3. 通常直接一致を全体一対一で割り当てる。
4. 同一Invoice等で明示的に結びつく返金純額を割り当てる。
5. 同一法人カード・同一販売者・同一通貨の後日返金純額を全体最適化する。
6. 返品・取消行には、元決済を`reference`として保存する。
7. 金額計算に使った構成要素を`consume`として保存する。
8. DB一意制約で、同じフィンガープリントの二重`consume`を最終防止する。

## 4. 所有権競合

- 管理者確定があれば管理者確定を維持する。
- 自動割当同士なら時系列の早い明細が優先する。
- 先行明細が後続明細の構成要素を取得した場合、後続明細の計算全体を解放する。
- 解放された明細は未一致へ戻し、再照合マーカーを付ける。
- 並行処理でDB一意制約へ衝突した場合、トランザクションをロールバックして1回再試行する。

## 5. 未消費書類スナップショット

1. 対象月または実明細に関連する月跨ぎPDFだけを表示対象にする。
2. 各PDFの全構成要素について、現在明細・他明細の`consume/reference`履歴を取得する。
3. 少なくとも1構成要素が未消費ならPDFを表示する。
4. 一部使用済みの場合は、各構成要素の状態と使用先を表示する。
5. 全構成要素が消費済みなら表示しない。
6. 解析できないPDFは「解析要確認」として残す。

## 6. 次月への引き継ぎ

前月明細Aで使用したフィンガープリントはDBに残る。翌月明細Bを照合するとき、Aの`consume`所有は予約済み候補として除外される。

```text
2026-07 明細A
A = あ + い + う
→ あ・い・うをconsume保存

2026-08 明細B
Bの候補に「い」があっても、Aが所有済み
→ いを除外して別構成を探索
→ 別構成がなければBは未一致
```

## 7. 領収書・明細の変更

- 領収書追加／差し替え：その金融イベントの最古月以降を再照合待ちにする。
- 領収書削除：履歴行のスナップショットとフィンガープリントは保持し、残存明細を再照合待ちにする。
- 明細削除：その明細が所有していた`consume`を解放し、残存明細を再照合待ちにする。
- 管理者操作：操作前後の明細内`consume`集合が変化した場合、他明細のスナップショットと割当を更新する。
