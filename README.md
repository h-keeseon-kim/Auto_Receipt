# ReceiptHub

**Version: 1.16.0**

ReceiptHubは、社内で利用しているサブスクリプション、従量課金/API、一回払いサービスの領収書を月単位で回収・検査・管理するDjangoアプリです。

バージョンはリポジトリ直下の `VERSION` に記録します。Web画面には表示しません。

## v1.16.0 月跨ぎ明細・法人カード返金相殺・返品再計上の照合

7月のカード明細に6月末の決済が含まれるケース、同一法人カードへ複数アカウントの返金が後日まとめて反映されるケース、元売上の返品と差引後金額の再計上が併記されるケースを、保存済みの明細行と領収書から厳密に照合します。

主な変更点は次のとおりです。

- 明細PDF内の実利用日から必要な領収書発行月を自動算出し、明細月だけでなく前月分も候補へ追加
- 通常決済は従来どおり、金額・通貨完全一致、請求元一致または監査済み決済名義互換、日付差±1日で全体一対一割当
- Refund／Credit Noteは、同一法人カード・同一請求元・同一通貨の範囲で、異なる利用者・Invoiceを含む後日返金として最大45日後まで探索
- 複数明細を同時に最適化し、1つの返金構成要素を複数明細へ重複使用しない
- 返品・取消行は通常売上と分離し、同日・同一請求元の元決済領収書を決済グループ内で参照
- 1つのRefund PDFに含まれる元決済と返金を別構成要素として扱いつつ、未使用一覧では物理PDFを1件として表示
- `GOOGLE PLAY JAPAN`、`Google One`、`Google AI Ultra`、`Google Asia Pacific Pte. Ltd.`の既知請求経路を正規化し、Google Cloudとは分離

2026年7月明細の回帰ケースとして、次を固定テストしています。

```text
0415: 松﨑 Google One 32,000 JPY（7/11） ↔ GOOGLE PLAY JAPAN 32,000 JPY（7/10）
0424: 295.54 - (0.71 + 0.90 + 32.37 + 12.41 + 65.58 + 4.97) = 178.60 USD
0465: 110.00 - (4.62 + 0.64) = 104.74 USD
0466: 220.00 - (119.20 + 34.20) = 66.60 USD
0383: 0466と同じ220.00 USD元決済を返品元証拠として参照
```

通常利用の証憑にはReceiptまたはInvoiceを使用できますが、返金の証憑にはRefund／Credit Noteまたは明示的な返金構成要素が必要です。

## v1.15.5 決済名義とサービス名の請求経路照合

カード明細のご利用先が購入サービス名ではなく決済チャネル名になる場合を、厳格な既知対応として扱います。最初の対応はGoogle Play決済とGoogle Oneです。

```text
明細 0415
2026-07-10 / GOOGLE PLAY JAPA / 32,000 JPY

提出書類
2026-07-11 / Google One / 32,000 JPY

結果
決済名義互換一致
```

金額・通貨の完全一致と利用日±1日は従来どおり必須です。Google Cloudはこの互換グループに含めません。同じ金額のGoogle One明細が別日に存在しても、全体一対一割当によって近接する正しい書類を使い、サービス名が完全一致する組み合わせを互換一致より優先します。

明細に紐づかなかった提出書類の「最も近い明細」は、すでに別の書類で一致済みの明細を除き、未一致・解析要確認として残った明細だけから選びます。

## v1.15.4 全社明細月と領収書発行月の一致

ご利用代金明細の月と、照合対象の領収書発行月を同じ月へ統一しました。

```text
ご利用代金明細月 2026年07月
→ 領収書発行月 2026年07月
→ 内部提出サイクル 2026年08月に保存された領収書を照合
```

旧仕様では2026年7月明細が2026年7月提出サイクル（2026年6月発行の領収書）を参照していました。v1.15.4以降は、ユーザー画面で「領収書発行月 2026年7月」を選んで登録した領収書を参照します。既存明細には再照合マーカーを付け、明細PDFをOpenAIへ再送信せず、保存済み明細行を新しい月次ルールで再照合します。

領収書の追加・差し替え・AI解析結果更新時も、内部提出サイクルから領収書発行月を逆算し、同じ月の全社明細だけを再照合待ちにします。

## v1.15.3 管理者の月別状況・代理アップロード修正

管理者が提出履歴から一般ユーザーの「月別状況」または「代理アップロード」を開いた際、対象領収書月の計算結果をテンプレートへ渡す変数が未定義となり500を返していた問題を修正しました。選択した提出サイクル月から `receipt_month_for_submission()` で領収書発行月を必ず算出してから画面を描画します。

```text
提出サイクル月 2026年08月
→ 対象領収書月 2026年07月
```

この画面は月別状況と代理アップロードで共通のURL・ビューを使用するため、両方の導線が同時に復旧します。

## 月の定義

一般ユーザーは、画面上で**領収書発行月**を直接選択します。内部では、その翌月を提出・リマインダー・全社明細照合の月次サイクルとして保持します。

```text
領収書発行月 2026年06月 → 内部提出サイクル 2026年07月
領収書発行月 2025年12月 → 内部提出サイクル 2026年01月
```

ユーザー画面には内部提出サイクルを表示せず、領収書発行月だけを基準に操作します。AIの日付確認、利用停止時の最終領収書月、API利用なし申告、カード明細照合、リマインダーメールは同じ対応関係を使用します。

### 月選択フォームの表示

月を変更すると自動的に対象月へ切り替わります。ブラウザー標準の月入力は、選択月とは別に現在月を枠線で表示するため、ReceiptHub独自の月選択UIを使用します。選択中の業務対象月だけを青色で表示し、現在月を別枠で強調しません。2026年8月に直接開いた場合、領収書発行月とご利用代金明細月はいずれも2026年7月を初期表示します。

操作上不要な「月を選ぶと自動で切り替わります。」という説明文は表示せず、ラベルと月入力だけを表示します。ページ幅が不足する場合は月選択フォーム全体を次の行へ移し、760px以下ではラベルと入力を縦並びにして、文字や入力欄がカード外へはみ出さないようにします。


## v1.15.1で実現する最終フロー

### 契約変更情報から未提出明細を「推定対応」へ分類

当月の直接領収書が存在しない場合でも、契約変更書類にBill toメール、旧プラン、新プラン、旧プラン終了日が明記され、前月の全社カード明細に同一請求元・完全一致金額・同一請求周期の実績がある場合は、赤い未一致ではなく管理者確認前の`推定対応`として表示します。前月カード明細は領収書提出の証拠ではなく、旧プラン金額と請求周期を裏付ける補助証拠です。

```text
当月の契約変更書類
  Bill to: 対象ユーザーのメール
  旧プラン: Claude Pro
  新プラン: Max plan - 20x
  旧プラン終了日: 2026-06-08

前月カード明細
  Anthropic / 2026-05-08 / 22.00 USD

当月未一致明細
  Anthropic / 2026-06-08 / 22.00 USD

結果
  推定対応（管理者確認待ち）
```

同額の別候補がある場合でも、旧プラン終了日との日付差、前月請求日との周期、請求元、金額・通貨の完全一致を優先し、契約変更書類と前月実績はそれぞれ1明細にだけ使用します。管理者は`推定対応を一致として確定`または`推定を採用せず未一致`を選択します。

### 管理者画面の情報整理

提出履歴の上部集計は`AI未確認`と`未提出ユーザー（API利用確認待ちを含む）`だけに整理しました。月選択は内部提出月ではなく`領収書発行月`を表示し、初期値は現在月の前月です。提出状況一覧ではAPI確認待ちだけを残し、アップロード済み領収書の絞り込みは`すべて / 再提出判断待ち / 確認が必要 / AI未確認`に限定します。

ご利用代金明細の集計は`明細行 / 解析要確認 / 未一致（推定対応を含む） / 明細未使用の提出書類`だけを表示します。結果絞り込みボタンは`未一致 / 解析要確認`の2つに整理します。`未一致`を選ぶと、結果を`推定対応`、`未一致`、`明細に紐づかなかった提出書類`の3区分に分けて表示します。推定対応だけの独立ボタンは表示しません。

## v1.14.2で実現する最終フロー

### v1.14.2 領収書アップロードと明細再照合の分離

領収書の保存処理ではカード明細の全件再照合を同期実行しません。領収書を先に確実に保存し、同じ月のカード明細へ再照合待ちマーカーを付けます。管理者が「ご利用代金明細」ページを開いた時、または「最新の領収書と再照合」を押した時に、保存済みの最新領収書で一度だけ再照合します。

これにより、既存領収書の金融・契約変更メタデータ補完が`Receipt.post_save`を再帰的に発火して、ユーザーまたは管理者のアップロード要求をタイムアウトさせる問題を防ぎます。アップロード診断は次で実行できます。

```bash
python manage.py diagnose_receipt_upload
```

### v1.14.1 契約・プラン変更情報による推定対応

通常の当月領収書照合で未一致となったカード明細について、当月の契約変更書類に明記された旧プラン終了情報と、同一ユーザーの過去月の旧プラン領収書を組み合わせ、管理者確認前の「推定対応」を提示します。

例えば、当月のAnthropic領収書に `Unused time on Claude Pro after 06 Jun 2026`、旧プラン期間 `Jun 6–Jun 8, 2026`、新プラン `Max plan - 20x` が明記され、同一ユーザーの前月Claude Pro領収書が22 USD・同じ請求周期で存在する場合、6月8日のAnthropic 22 USD明細を推定対応として提示します。

推定は次の必須条件をすべて満たす場合だけ作成します。

```text
当月の通常照合では未一致
請求元グループ一致
契約変更書類に旧プラン名と旧プラン終了日を明記
明細利用日が旧プラン終了日の±1日
契約変更書類と過去領収書が同一ユーザー
過去領収書に旧プラン名を明記、または旧プラン名を抽出できない場合は同一ユーザーの定期契約サービスであること
過去領収書が前月で、明細と金額・通貨完全一致
過去の請求日と今回明細日が±1日
同じ証拠を複数明細へ重複使用しない
```

推定対応は直接一致ではありません。管理者画面では橙色で表示し、契約変更書類・過去領収書・旧新プラン・変更日・旧プラン終了日・金額・請求周期を確認できます。管理者が「一致として確定」または「推定を採用せず未一致」を選択し、判断結果は再照合後も維持します。

AIファイル名修正・検査では、AI抽出プラン名と契約変更情報を領収書レコードへ保存します。v1.14.0以前にAI確認済みだった領収書は、管理者の領収書確認画面から「AIで再検査（契約変更情報を更新）」を明示的に実行できます。通常の一括AI処理は、従来どおり処理済み領収書を再検査しません。

### 領収書プレビュー

管理者の領収書確認画面では、領収書ファイルを同一オリジンのiframe内へ表示します。プレビュー配信エンドポイントだけ `X-Frame-Options: SAMEORIGIN` を返し、ReceiptHub自身の確認画面からの埋め込みを許可します。その他の画面は従来どおりクリックジャッキング対策の `DENY` を維持します。表示できないブラウザー向けに「別タブで開く」も用意しています。



### v1.13.0 サービス名と法的販売者の分離・未使用提出書類

領収書本文から、法的な販売者名と製品・サービス・プラン名を別項目として保存します。例えばGoogle Oneの請求書では、法的販売者は`Google Asia Pacific Pte. Ltd.`、サービス名は`Google One`です。ファイル名とカード明細照合では、本文にサービス名が明示されている場合はサービス名を優先します。

```text
法的販売者: Google Asia Pacific Pte. Ltd.
サービス名: Google One
生成ファイル名: 260623_keeseon.kim_Google_One_32000_JPY.pdf
```

ご利用代金明細画面では、`すべて / 未一致 / 解析要確認 / 一致 / 対象外`の絞り込みを追加します。さらに、対象月に提出済みでありながら明細のどの行にも使われなかった領収書を「明細に紐づかなかった提出書類」として表示します。日付が近い同一請求元の明細と金額が異なる場合は、両方の金額を表示し、カード明細側の誤記、別取引、領収書不足を管理者が判断できます。

### v1.12.0 領収書抽出と明細照合画面

PDF領収書に検索可能な埋め込みテキストがある場合は、OpenAIへPDF本体と同じテキストを補助入力として渡します。OpenAIが金額・日付・通貨を返さなかった場合やAPI呼び出しが失敗した場合も、`Amount paid`、`PAID`、`Total`、`Payment Date`、`Issue date`などの明確なラベルから安全に補完します。画像PDFへOCRを繰り返す処理ではありません。

AIの総合判定が「要確認」であっても、明確に抽出できた金額・日付・通貨はDBへ保存します。宛名など別項目が未確認であることを理由に、カード明細照合に必要な金額・日付まで失わない設計です。

ご利用代金明細の照合結果は横長テーブルではなく、明細ごとのカード表示にします。各カードには明細番号・利用日・ご利用先・金額・一致状態・対応領収書・管理者操作だけを表示し、利用者を推定する表示や照合候補一覧は持ちません。1180px以下は2列、760px以下は1列へ切り替わり、長い横スクロールを必要としません。

### 一般ユーザー

1. ログインすると「利用サービス」が最初に表示されます。
2. サービスマスターに登録済みのサービスは「サービス利用登録」から選択し、Pカードを利用するか必ず指定して、管理者承認なしで利用中サービスへ追加します。
3. サービスマスターに存在しない新規サービスだけ、サービス名・支払い方法・Pカード利用有無・用途を入力して「新規サービス例外申請」を提出します。管理者の承認後にサービスマスターと利用中サービスへ追加されます。
4. 利用サービス一覧ではPカード利用有無を確認でき、支払い方法が変わった場合は後から設定を修正できます。Pカード未使用サービスは利用中のまま残りますが、領収書提出・リマインド・全社明細照合の対象外です。利用しなくなったサービスは停止します。Pカード利用サービスを停止する場合だけ、最後に提出すべき領収書月を指定します。
5. 毎月の「アップロード」で、何月に発行された領収書を提出するか「領収書発行月」を直接選択します。月を変更すると「表示」ボタンを押さずに対象月へ自動で切り替わります。登録済みサービスを選び、「＋ 領収書を追加」から1件または複数件のファイルを追加します。同じサービスへ後から1件ずつ追加した場合も既存ファイルを置き換えず、別の領収書として追記します。複数ファイル入力では、ファイルを分けて選択・ドロップしても選択済み一覧へ追加されます。
6. 返金・プラン変更・追加請求など登録サービス外の領収書は、サービス欄の「その他」を選び、必須メモ付きで追加します。
7. 従量課金/APIサービスを選択した領収書発行月に利用していない場合は、「この月は利用なし」を申告します。
8. 選択した領収書発行月のPカード利用サービスについて、領収書またはAPI利用なし申告が揃うと提出できます。Pカード未使用サービスは提出対象数へ含めません。
9. 管理者が「AIでファイル名を修正・検査」を実行すると、未処理の領収書だけが検査されます。
10. AIが不一致候補または確認不能項目を検出しても、領収書は自動削除されず、管理者の確認対象として保持されます。
11. AI検査が完了すると管理者画面の「再提出依頼」が有効になります。管理者が問題ありと判断して実行した場合だけ、対象領収書を提出項目から取り下げ、アプリ内通知と再提出依頼メールを送ります。
12. 提出履歴では登録サービスを「必須提出（サブスク等）」と「利用時提出（API等）」に分け、ファイル数ではなく対応済み・未対応サービス数で進捗を確認します。

### 管理者ユーザー

1. 「提出履歴」で対象月のユーザー別進捗を確認します。
2. ユーザーがファイルをアップロードできない場合は、ユーザー別月次ページの「管理者代理アップロード」から対象サービスとファイルを選び、本人に代わって登録します。代理アップロード欄のユーザー選択・前後移動から、提出履歴へ戻らず別ユーザーへ連続して切り替えられます。 提出月を変更すると「表示」ボタンを押さずに該当月へ自動で切り替わります。
3. 代理アップロード後は「確認」から領収書本体をプレビューし、AI検査、確認チェック、表示ファイル名の補正、管理者確認済みの確定まで行います。
4. 未提出サービス、API利用確認待ち、AI要確認、再提出判断待ち、再提出待ちを一覧で把握します。
5. 「アップロード済み領収書」は、再提出判断待ち・確認が必要・AI未確認・AI処理中・AI確認済み・管理者確認済み・ファイルなしに分類されます。ステータスタブを切り替えると、対応が必要な領収書だけを確認できます。
6. 領収書一覧は「利用者 / 領収書月」「サービス / ファイル」「確認状況」「操作」の4列です。AIチェックリスト、払先、宛名、カード番号、管理者メモは必要な行だけ展開して確認します。デスクトップでは4列内で情報を折り返して長い横スクロールをなくし、狭い画面ではカード表示へ切り替わります。
7. 「AIでファイル名を修正・検査」を押すと、未処理の領収書だけをバックグラウンド処理します。処理中は「AI処理中」、完了した領収書は完了順に該当ステータスへ移動し、タブ件数と一覧へリアルタイム反映されます。 処理対象がないため無効になっている場合は通常の無効カーソル、実際に処理中の場合だけ待機カーソルを表示します。
8. AI検査が完了すると「アップロード済み領収書」の各行にある「再提出依頼」が有効になります。AIが問題候補とした領収書は「再提出判断待ち」、曖昧・未確認項目がある領収書は「確認が必要」として表示されます。管理者が問題ありと判断した場合だけ再提出を依頼し、問題なければ「再提出不要として確認済み」にします。
9. 「利用サービス管理」のユーザー別サービス状況で、各サービスのPカード利用有無を確認・変更できます。ユーザー別月次ページでは、Pカード利用サービスごとの領収書提出状況と、Pカード未使用の提出不要サービスを分けて確認できます。
10. 「ご利用代金明細」で会社全体のPカード明細を1件アップロードすると、AIが全明細行を抽出し、Pカード利用サービスについて、明細月と同じ領収書発行月の全ユーザー領収書を一括照合します。例えば7月分明細は、ユーザーが領収書発行月7月として登録した領収書（内部提出サイクル8月）と照合します。
11. 各PDFを支払済み領収書・請求書・返金書類へ分類し、元決済・返金・Payment historyを取引構成要素として抽出します。明示Invoice/Transaction IDで重複を除外した後、金額・通貨完全一致、請求元一致、利用日±1日の直接一致を全体一対一割当し、必要に応じて返金書内の元決済、明示的に紐付く返金相殺、同一請求元内の近接返金相殺を確認します。利用者は照合条件に含めません。対応PDFはあるが必要項目を解析できない行は「解析要確認」、証拠を確認できない行は「未一致」として赤色表示します。
12. 通常の明細照合で未一致となった行について、契約変更書類と同一ユーザーの過去旧プラン領収書が厳格条件で一致する場合は「推定対応」として橙色表示します。管理者が根拠を確認し、「一致として確定」または「推定を採用せず未一致」を選択します。
13. 解析・照合完了後に「照合結果PDF」をダウンロードし、権限を限定したSlackチャンネルへ共有できます。
14. 「サービス例外申請」で、サービスマスターに存在しない新規サービスの申請だけを確認し、承認または却下します。承認時は新しいサービスマスターと対象ユーザーの利用サービスへ反映されます。
15. 「利用サービス管理」は「サービスマスター」と「ユーザー別サービス状況」をタブで切り替えて管理します。サービスマスターでは各サービスを現在利用しているユーザー名とPカード状態を展開表示し、そのユーザーのサービス状況へ直接移動できます。
16. 「ユーザー管理」でユーザー追加・削除・ステータス・パスワードを管理します。スーパーアカウント設定はページ最下部に表示します。
17. 再提出依頼を実行すると「再提出依頼管理」へ登録され、対象ユーザーへメールを送信します。依頼管理では1件ずつ削除、表示月単位で一括削除、または全期間・全状態の依頼を一括削除できます。
18. 「メール送信」でリマインダー日、件名、本文、テスト送信を管理します。

### スーパーアカウント

- 一般ユーザーと管理者ユーザーの権限を切り替えられます。
- 管理者ユーザーの作成・削除・パスワード変更も行えます。
- 一般の管理者ユーザーは、他の管理者ユーザーの権限・削除・パスワードを操作できません。

### サービス管理

- 一般ユーザーと管理者の双方が、登録後にPカード利用有無を変更可能
- 既存サービスはv1.8.0移行時にすべてPカード利用として初期化
- サービスマスターに存在しない場合だけ利用できる新規サービス例外申請（サービス名・支払い方法・用途）
- 管理者画面の未対応通知、承認・却下、承認時のサービスマスター自動作成
- 承認前は利用サービスへ追加せず、承認後に「例外申請承認」として対象ユーザーへ登録
- 一般ユーザーによる利用停止と最終領収書月の指定
- サービス利用状況に応じたユーザーステータス自動同期

### Pカード利用設定

Pカード利用有無はサービスマスターではなく、**ユーザーごとの利用サービス**に保存します。同じChatGPT（サブスク）でも、ユーザーAはPカード利用、ユーザーBはPカード未使用として個別管理できます。

サービス利用登録・例外申請・管理者代理登録では、初期値を自動選択せず、次のいずれかを必ず明示的に選択します。

```text
Pカード利用
Pカード未使用
```

Pカード利用サービスだけが次の対象です。

- 領収書アップロードのサービス選択肢
- 月次の必須提出・API利用確認
- 4日・10日のリマインドメール
- 全社ご利用代金明細との照合対象

Pカード未使用へ変更しても、過去の領収書ファイルと提出履歴は削除しません。領収書にはアップロード時点のPカード設定を監査用スナップショットとして保持します。

その月にPカード利用サービスがなく、「その他」の領収書や再提出依頼もない場合、ユーザー画面と管理者画面の月次ステータスは「提出不要」と表示し、提出ボタンも表示しません。

### サービス例外申請フロー

サービスマスターに登録済みのサービスは、一般ユーザーが「サービス利用登録」から直接選択します。この操作は例外申請ではなく、管理者承認も必要ありません。

「サービス利用登録」の一覧に存在しない新規サービスを使いたい場合だけ、次の内容で例外申請を提出します。

- サービス名
- 支払い方法（サブスク / 従量課金・API / 一回払い / その他）
- Pカード利用有無
- 用途

申請直後の状態は「確認待ち」で、利用サービスや領収書アップロードの選択肢には追加されません。管理者には上部メニューの件数バッジと画面内通知が表示されます。

申請画面で入力したサービス名・支払い方法がすでにサービスマスターに存在する場合は、例外申請を受け付けず「サービス利用登録」へ案内します。停止中のマスターが存在する場合は、管理者への再開依頼を案内します。

管理者が承認すると、新しいサービスマスターを自動作成し、その後、対象ユーザーへ利用サービスを登録してユーザーステータスも同期します。申請後に同じマスターが別経路で登録された場合だけ、重複作成を避けて既存マスターを利用します。却下時は理由の入力を必須とし、ユーザーは利用サービス画面の申請履歴から確認できます。

同じユーザー・同じサービス名・同じ支払い方法の確認待ち申請は重複提出できません。同じ名前でも支払い方法が異なる申請は別申請として扱います。

### 一般ユーザーの月次画面UX

- 「サービス利用登録」の一覧に目的のサービスがない場合は、同じ画面内の青い案内枠から「新規サービス例外申請」へ進む
- 例外申請画面には「サービス利用登録へ戻る」を常設
- アップロード画面では「領収書発行月」だけを選択し、内部の提出月は表示しない
- 未完了の状態は「下書き」ではなく「未提出領収書あり」と表示
- 一部サービスが残っていてもアップロード済み領収書は保存し、黄色の注意文で残りを案内
- 提出履歴では、サービス登録数を「必須提出（サブスク等）」と「利用時提出（API等）」に分けて表示
- 月次進捗はファイル数ではなく、対応済みサービス数と未対応サービス数で表示（APIの「この月は利用なし」も対応済みとして集計）
- ユーザー画面ではファイル保存期限を表示しない

### 月次領収書提出

月次提出の対象は、そのユーザーのPカード利用サービスだけです。Pカード未使用サービスは利用中サービス一覧には残りますが、未提出数、API利用確認待ち、提出可否、リマインド対象には含めません。

- PDF / PNG / JPG / JPEG / WEBP対応
- 領収書・管理者代理アップロード・ファイル差し替え・全社ご利用代金明細書でドラッグ＆ドロップ対応
- 複数回に分けたアップロード
- サービス選択後に「＋ 領収書を追加」を表示し、ファイル選択時に自動アップロード
- 1回のファイル選択で複数ファイルを追加可能
- 同じサービスへ追加操作を繰り返し、領収書を何件でも登録可能
- 全ユーザーのサービス選択肢に「その他」を常設
- 「その他」は内容メモ必須で、登録サービスの提出済み判定には流用しない
- 提出後に登録サービスまたは「その他」の領収書を追加すると「未提出領収書あり」へ戻し、再提出可能
- 提出後もファイル差し替え可能
- 月別提出履歴・詳細確認
- 従量課金/APIサービスの「この月は利用なし」申告
- 選択した領収書発行月の全サービスが解決するまで提出完了不可
- 管理者が再提出を依頼した領収書は一覧から削除され、再アップロード可能
- 管理者がユーザー別月次ページから、対象ユーザーの登録サービスまたは「その他」を選んで代理アップロード可能
- 管理者代理アップロードはユーザー画面にも即時反映し、通常のAI検査・カード明細照合・再提出フローの対象になる
- 管理者専用の領収書確認画面でPDF・画像をプレビューし、AI結果、7つの必須確認項目とカード末尾の任意確認項目、表示ファイル名、管理者メモを確認・補正可能
- カード末尾を除く必須確認項目が揃った領収書を「管理者確認済み」として確認者・確認日時付きで記録
- AIは再提出依頼を自動作成せず、管理者確認画面から「再提出不要として確認済み」または「再提出を依頼」を選択可能
- 再提出依頼は個別、表示月単位、全期間単位で削除可能。削除するとユーザー画面の通知も消える
- アップロード元と実行者を監査情報として保存し、画面とZIP内 `manifest.csv` で確認可能
- 提出済み月へ管理者が追加した場合は「未提出領収書あり」へ戻し、ユーザーの再提出対象にする

### OpenAIによる領収書検査

AI処理はユーザーのアップロード中には実行しません。管理者が提出履歴のボタンを押した時だけ、未処理の領収書を検査します。月の一致判定では提出月そのものではなく、その前月に当たる対象領収書月を使用します。

確認項目:

- 支払カード末尾4桁が記載されている場合、`RECEIPT_CARD_LAST4` と一致するか（任意の補助確認項目。未記載はエラーにしない）
- 領収書上の払先を確認できるか
- 領収書の利用者名・宛名が対象ユーザーと一致するか
- 登録サービスと払先に合理的な関連があるか
- その他領収書では、必須メモと領収書内容に合理的な関連があるか
- 日付を確認できるか
- 金額を確認できるか
- 通貨を確認できるか
- 領収書日付の年月が、提出月の前月に当たる対象領収書月と一致するか

サービス名と払先は完全一致を前提にしません。

- `ChatGPT（サブスク）` と `OpenAI`
- `Claude（サブスク）` と `Anthropic`

のような提供元・請求元の関係を判定します。サービスマスターの「カード明細・払先の表記候補」もAIへ渡します。

「その他」の追加領収書では、ユーザーが入力した必須メモもAIへ渡します。メモは返金・プラン変更などの背景を理解するための参考情報であり、領収書ファイル内の払先、日付、金額、通貨を優先します。カード末尾は記載がある場合だけ補助証拠として抽出します。メモと領収書が明確に矛盾する場合も自動取り下げはせず、再提出候補として管理者確認対象にします。

#### 再提出候補と管理者判断

次のようにAIが明確な不一致候補を検出しても、領収書と実ファイルは保持し、再提出依頼を自動作成しません。

- カード末尾4桁が対象カードと違う
- 利用者名・宛名が対象ユーザーと明確に違う
- サービスと払先が明確に無関係
- 「その他」の必須メモと領収書内容が明確に矛盾する
- 領収書日付の年月が対象領収書月と違う

対象領収書には「再提出判断待ち」と理由を表示します。管理者は領収書プレビューを確認し、次のどちらかを選択します。

- 問題なし: チェックを補正し、「再提出不要として確認済みにする」
- 問題あり: AI検査完了後に有効になる「再提出依頼」を一覧から実行するか、確認画面でユーザー向け理由を入力して「再提出を依頼」

再提出を依頼した時点で初めて対象領収書と実ファイルを提出項目から削除し、提出済み月を「未提出領収書あり」へ戻します。依頼は「再提出依頼管理」へ登録され、ユーザー画面の通知に加えて、登録メールアドレスへ再提出依頼メールを送信します。メール送信結果は「メール送信」のログで確認できます。

#### 曖昧・確認不能

AIが断定できない項目はチェックを付けず、領収書は保持します。管理者画面でハイライトし、管理者用メモとチェックリストを表示します。一般ユーザーにはAI内部メモを表示しません。

利用者名・宛名は、領収書の `Billed to`、`Bill to`、`Customer`、`Account holder`、宛名、購入者名などを抽出し、対象ユーザーの登録氏名・メールアドレスと照合します。宛名が会社名や部署名だけ、記載がない、または表記だけでは個人を特定できない場合は未チェックのまま管理者が確認します。宛名チェックはファイル名作成可否とは独立しており、宛名だけ曖昧でも他項目が揃えばファイル名候補は保持します。

#### ファイル名

確認できた情報から、表示・ダウンロード用ファイル名を次の形式で生成します。

```text
YYMMDD_ユーザー名_企業名または短い取引ラベル_金額_通貨.拡張子
```

例:

```text
260602_test_Anthropic_220_USD.pdf
```

その他領収書では、領収書本体を優先しつつ必須メモを補助情報にして、例えば次のような短いラベルを生成できます。

```text
260602_test_OpenAI返金_220_USD.pdf
```

ユーザー名部分は、Djangoの姓が設定されていれば姓、未設定ならメールアドレスの `@` より前を使います。内部ストレージ上の物理ファイル名は衝突防止用のUUIDを維持します。

### ご利用代金明細書の全ユーザー照合

全社明細はPカードの利用履歴であるため、照合対象サービスと通常領収書はPカード利用として登録されているものに限定します。「その他」の追加領収書も、PDF本文から取引構成要素を抽出できる場合は照合対象にします。

管理者は専用の「ご利用代金明細」ページから、会社全体のカード明細を**明細月**ごとにアップロードします。ユーザーは選択しません。AIが明細表の全行を抽出した後、**明細月と同じ領収書発行月**としてすべての一般ユーザーが登録した領収書を横断して、一対一で照合します。例えば2026年07月分明細は、領収書発行月2026年07月として登録され、内部的に2026年08月提出サイクルへ保存された領収書と照合します。

AIは明細PDFから次を抽出します。

- カード末尾4桁
- 請求・支払対象月
- 支払日
- 明細番号
- 利用日
- ご利用先
- 円請求額
- 外貨額・通貨
- 領収書が必要か

明細月は利用日の月ではなく請求・支払月として扱います。例えば6月利用、7月27日支払いの明細は7月分であり、ReceiptHubでは**7月提出サイクルの6月分領収書**と照合します。

#### v1.12.0の実データ検証

2026年7月分の全社明細61行と提出PDF63件を、ファイル名ではなくPDF本文で全件監査しました。

```text
一致                          59件
├ 直接一致                    56件
├ 返金書内に記録された元決済    1件
├ 明示的に紐付く返金の相殺       1件
└ 同一請求元内の近接返金相殺     1件
未一致                         2件
```

この結果から、単純な「1 PDF = 1領収書」方式を廃止し、各PDFに含まれる金融イベントを**取引構成要素**として扱います。

#### 照合順序

```text
1. PDF本文から書類区分・元決済・返金・支払履歴を抽出
2. Invoice / Receipt / Transaction IDが同じ証拠を重複除外
3. 金額・通貨完全一致、請求元一致、利用日±1日の直接一致を全体最適化で一対一割当
4. 返金書類内に記載された元決済を確認
5. 元決済と明示的に紐付く返金を相殺
6. 同一請求元内で利用日±1日の近接返金を相殺し、正味額が完全一致するか確認
7. 未一致行だけ、契約変更書類と同一ユーザーの過去旧プラン領収書から推定対応を評価
```

利用者名は照合条件に含めません。誰の利用かではなく、明細行数に対して必要な証拠数が存在するかを確認します。

自動照合の請求元はPDF本文から抽出した払先だけを使用します。ユーザーが選択した登録サービス名や「その他」メモは、払先を読み取れなかった場合の代用品にはしません。払先を抽出できない提出ファイルは、誤一致させず「解析要確認」にします。

#### 金額・通貨

許容差はありません。

```text
22.00 USD と 22.00 USD   一致可能
22.00 USD と 22.01 USD   不一致
15,400 JPY と 15,401 JPY 不一致
```

外貨明細は外貨金額と通貨、円建て明細は円請求額を比較します。外貨額と円換算額を直接比較しません。

#### 重複排除

重複は明示Invoice番号、Receipt番号、Transaction ID等が同じ場合だけ除外します。同じ払先・金額・日付だけでは重複扱いにしません。同日に同じサービスの同額決済が複数発生するためです。

照合目的は「カード明細行に対応する提出PDFがあるか」の確認なので、本文から請求元・取引日・金額・通貨を確認できるInvoiceも提出証拠として扱います。支払済み領収書と請求書が同じ取引を示す場合は、明示Invoice番号で重複排除し支払済み領収書を優先します。返金書類のPayment historyに元決済が掲載されている場合、元決済と返金を別構成要素として保存します。

#### 返金相殺

直接一致で解決しない場合、次を順番に確認します。

```text
元決済 + 明示的に紐付く返金 = 明細額
元決済 + 同一請求元・同一通貨・同一明細月の返金 = 明細額
```

いずれも正味額が完全一致する場合だけ照合します。1つの取引構成要素は1明細行にしか使用しません。

#### 解析要確認と未一致

提出ファイルがあるものの、取引日・金額・通貨・払先を抽出できない場合は、未提出と断定せず**解析要確認**として黄色表示します。管理者が領収書AI再検査または手動確認を行います。

対応する提出証拠を確認できない場合だけ次の状態にします。

```text
一致状態：未一致
領収書状態：未提出
画面表示：赤色ハイライト
```

同一請求元・金額・通貨の明細数に対して、明示参照番号で重複を除外した決済証拠数が少ない場合は、必要数と不足数を判定メモに表示します。

管理者が領収書不要の明細と判断した場合だけ「領収書対象外にする」を使用します。新しい領収書がアップロードされた後は「最新の領収書と再照合」を押すと、明細PDFをOpenAI APIへ再送信せず、保存済み明細行と最新の提出PDFで再照合します。

詳細仕様は `docs/MATCHING_RULES_v1.14.1.md`、実データ監査の概要は `docs/EMPIRICAL_AUDIT_2026-07.md` を参照してください。

#### 照合結果PDFとSlack共有

AI解析・領収書照合が完了すると、明細書カードに「照合結果PDF」ボタンが表示されます。ダウンロードされるPDFには次を含みます。

- 対象月、解析ステータス、カード末尾4桁、支払日
- アップロード・解析完了・最終照合日時
- 未一致（領収書未提出）・解析要確認の詳細
- 全明細行の照合結果

PDFでは、生成日時・Slack共有用表記、集計テーブル、解析メモ、ユーザー別要対応サマリー、利用者・サービス候補を表示しません。未一致行は赤色、解析要確認行は黄色でハイライトします。返金相殺では使用した提出ファイルと計算内訳も表示します。PDFは横向きA4・複数ページで生成され、長いご利用先名やファイル名はセル内で折り返します。

Slack APIへの自動投稿は行わず、管理者がダウンロードしたPDFを手動で共有する運用です。

### リマインダーメール

リマインド対象は、利用中ユーザーのうち、Pカード利用サービスに未提出・未確認項目があるユーザーだけです。Pカード未使用サービスだけを利用しているユーザー、またはPカード利用サービスの対応がすべて完了しているユーザーには送信しません。

Resend SMTPを使います。通常リマインダー日と警告日は管理者画面から変更でき、初期値は毎月4日と10日です。

#### 通常リマインダー

- 利用中の一般ユーザーだけが対象
- サブスク、一回払い、その他の未提出サービスがあるユーザーへ送信
- APIだけが未確認の場合は送信しない

#### 重要リマインダー

- 利用中の一般ユーザーだけが対象
- 未提出サービスまたはAPI利用確認待ちがあるユーザーへ送信
- 件名には必ず `【重要】` を付与
- 初期本文には「本日中」の案内を含む
- サブスク領収書は提出済みでもAPIサービスが未確認なら、APIを利用していないか確認するメールを送信

ユーザーがAPIサービスを対象領収書月に利用していない場合は、アップロード画面で「対象領収書月は利用なし」を選ぶと重要リマインダー対象から外れます。

管理者は「メール送信」で次を変更できます。

- 通常リマインダー日
- 警告日
- 通常メール件名・本文
- 重要メール件名・本文

利用可能なテンプレート変数:

```text
{app_name}
{user_name}
{target_month}
{receipt_month}
{upload_url}
{missing_services}
{api_pending_services}
```

送信ログを保存し、同一月・同一ユーザー・同一種別の重複送信を防止します。再提出依頼メールも同じ送信ログへ記録します。停止中ユーザーにはリマインダー、再提出依頼メール、テストメールを送りません。

## Railway運用

### Webサービス

- `railway.toml`
- Start Command: `/app/start.sh`
- Volume mount: `/app/media`
- PostgreSQLと同じ `DATABASE_URL`
- OpenAI・SMTP環境変数を設定

`start.sh` はデプロイ時にマイグレーションを適用してからGunicornを起動します。

### メール送信Cron

管理者画面で日付を変更できるため、4日用・10日用を分けず、毎日1回のCronサービスを1つ使います。

```bash
python manage.py send_receipt_reminders --kind auto
```

設定例は `railway-email-reminder-daily.toml` です。Cronは毎日起動し、管理者設定の日だけ送信します。

### AI処理

AI検査用Cron・Workerは不要です。管理者がWeb画面のボタンを押した時だけWebサービス内で実行します。

保守用CLI:

```bash
python manage.py process_pending_receipts --limit 100
```

### 期限切れ削除

期限切れ削除コマンドは、`/app/media` の実ファイルへアクセスできる実行環境で動かしてください。設定例は `railway-cron.toml` です。

### スーパーアカウントの連絡先メール

スーパーアカウントのログイン名は `admin` のまま維持し、連絡先メールアドレスは任意にできます。「ユーザー管理」の「スーパーアカウント設定」でメール欄を空欄にして保存すると、そのメールアドレスを一般ユーザーのアカウント名として再利用できます。

```bash
python manage.py clear_superuser_email --username admin
```

この操作はスーパーアカウントのログイン名・パスワード・権限を変更しません。
