# ReceiptHub

社内ツールの利用領収書・Invoice・返金書類を回収し、全社法人カード明細と照合するDjangoアプリです。
現在のバージョンは `VERSION` を参照してください。変更履歴は `CHANGELOG.md` に集約しています。
使い方・設定・照合仕様・検証手順はこのREADMEを更新し、バージョン別の説明書は作成しません。

## ご利用代金明細の月の定義

| 項目 | 意味 | 例 |
|---|---|---|
| 照合対象月 | 管理者が選択する利用分・領収書管理の月 | 2026年8月 |
| 利用日 | カード明細の各取引が発生した日 | 2026年8月3日 |
| カード支払日 | カード会社への引き落とし日。利用月とは別項目 | 2026年9月28日 |
| 領収書発行月 | ユーザー画面で選ぶ書類の対象月 | 2026年8月 |
| 内部提出サイクル | 保存上の月。領収書発行月Mの翌月M+1 | 2026年9月 |

支払日が9月でも、8月利用分を9月の領収書へ照合しません。AIの `statement_period` も利用対象月の意味で扱い、サーバー側では抽出済み利用日で独立に検証します。元のAI判定・原文メモと検証結果は `CardStatement.period_validation` に分けて保存します。

選択月の利用行が存在し、選択月より後の利用行がない場合に検証済みとします。選択月の利用行とともに前月以前の遅延計上行がある場合は、その利用月の領収書も照合候補へ含めます。通常の±1日判定が月初・月末をまたぐ場合も、隣接する保存サイクルの領収書を参照します。利用日が不明、選択月の行がない、未来月の行が混在する場合は要確認を維持します。支払月から一律に1か月引く処理や、選択月へ無条件に書き換える処理は行いません。前月行しかない特殊な明細は、現在の保守的ルールでは要確認です。

ファイル名の年月は月判定の根拠にしません。画面の原文メモを開いたときに旧AI判定が表示されても、それは監査用の抽出時記録で、現在の判定は「利用日による対象月検証」と照合結果です。

## 基本運用

一般ユーザーは管理者が登録した利用サービス、利用中／停止中の状態を確認します。既存マスターからのサービス申請と、未登録サービスの例外申請に対応します。アカウント作成・初期パスワード・初回パスワード変更は従来の機能を維持しています。

領収書はユーザー画面の領収書発行月を選び、サービス別にアップロードします。同月の追加提出・差し替え、管理者の代理提出に対応します。返金・プラン変更等は「その他」へ内容が分かるメモとともに登録します。通常利用はReceiptに加えInvoiceも照合証拠として許可しますが、未払いInvoiceが実際の支払証明になると保証するものではありません。返金はRefund／Credit Note等、本文に明示された金額だけを使用します。

AI検査は本文の販売者・サービス名・日付・金額・通貨・カード情報・金融イベントを抽出し、確認結果とファイル名へ反映します。管理者が明示的に単票／一括処理を開始する設計です。AI解析だけで書類を削除したり、領収書未提出を自動確定したりしません。再提出依頼・管理者確認・削除操作を区別します。

API／従量課金は、領収書がない月の「利用なし」申告に対応します。停止アカウントはメール対象外です。停止サービスは最終領収書月などのスコープを考慮します。通常の月次確認はPカード利用サービスが対象です。

## 全社明細の抽出・照合

明細書をアップロードすると、抽出した全取引行を保存してから証拠照合します。AIがサービスマスターを識別しただけの行を「一致」「提出済み」として保存しません。抽出後も証拠割当が完了するまでは処理中です。ポーリングは明細本体と画面上部の件数を同じ応答から更新します。

表示は以下を区別します。

- **一致／提出済み**：当該取引に対応する領収書または取引証拠が保存されている状態。
- **未一致／領収書未確認**：対応する証拠が未確認の状態。誰かの未提出とは自動断定しません。
- **解析・照合要確認**：日付・カード・月・書類解析などに確認事項がある状態。旧サービス分類だけの「一致」もこの表示へ補正します。
- **契約変更の推定対応**：既存の厳格な契約変更推定。管理者確定後も今月領収書の提出済みとは区別します。
- **提出者候補**：下記の問い合わせ先候補。未一致等の状態は変わりません。

通常照合は、正規化した請求元・サービス名、金額／通貨の完全一致、利用日と書類日の差±1日を条件に全体一対一で割り当てます。Google PlayとGoogle Oneは既知の決済名義互換として扱いますが、Google Cloudへ一律には拡張しません。外貨を円換算して近似金額で一致させる処理はありません。

Refund PDF内の元決済・返金を別構成要素として扱います。同一Invoice等に明示的に関連する返金純額を優先し、既存の法人カード単位・同一請求元・同一通貨の後日返金探索も維持しています。探索期間は明細日の14日前～45日後、1純額計算の返金は最大8件です。数学的な金額一致は決済代行会社の相殺処理を直接証明するものではないため、複数利用者をまたぐ割当は証拠内訳を管理者が確認してください。

### 月をまたぐ二重使用の防止

`CardStatementReceiptEvidence` は使用先明細・Receipt・構成要素・金額・通貨・日付・証拠識別子・ファイル名スナップショットを保存します。金融イベントの安定識別にはInvoice／Transaction ID等、またはファイルSHA-256と金融署名を使用します。ファイル名や再アップロード時のReceipt IDだけで使用済みを解除しません。

`consume` は金額計算への使用です。同じフィンガープリントは全明細で原則1回だけ消費でき、DB一意制約が最終的な重複防止を担います。`reference` は返品元確認等の非金額参照で、消費とは別です。前月Aで「あ・い・う」を消費した後、翌月Bで「い」を再び金額計算に使いません。

同じ明細の再照合はトランザクション内で自身の旧自動割当だけを解放し、再構築します。失敗した場合はロールバックします。管理者確定は自動処理より優先します。自動割当同士は明細月・アップロード日時・IDの順で先行する明細を優先し、後続の割当が競合した場合は、その金額計算グループ全体を再照合待ちへ戻します。

既存の履歴取得ロックは維持し、空値を許すReceipt関連は `prefetch_related` で別取得します。`SELECT FOR UPDATE` にnullableな外部結合を含めない修正も維持しています。

未消費書類の一覧は、今回だけでなく全明細で未消費の構成要素が残る対象月／関連月跨ぎPDFです。元決済だけ使用済みで返金が未使用なら「一部使用済み」、参照のみなら「参照済み・未消費」とし、使用先を示します。全構成要素が消費済みの書類や、内部探索だけに使う無関係な古い書類は表示しません。

## 前月履歴による提出者候補

今月の未一致・要確認の通常利用行について、前月の同じ請求元に関する提出履歴から、管理者が問い合わせる相手の候補を表示します。返金・取消行ではこの購入者候補推定を行いません。

定期課金は金額／通貨一致と翌月同日から3日以内の周期を有力な手掛かりとします。31日から月末への移動、12月から1月、うるう年を暦日で扱います。金額変更や周期不明は参考候補にとどめます。従量課金は月次固定請求とはみなさず、同額履歴は参考候補、変動額は前月に複数実績と近い日付がある場合だけ参考表示します。円／外貨の換算で候補を強化しません。

停止ユーザー・管理者アカウント・対象外のサービス・Pカード外サービス・明示的に別カードの書類・返金書類は候補から除外します。候補者は最大5人を表示し、同条件の複数人を一人に決めません。根拠、前月書類名・日付・金額、当月書類の有無を表示します。有力／参考はルール上の手掛かりの分類で、統計的な確率ではありません。

前月カードと直接照合された領収書の日付が月境界で1日ずれている場合、確定済みカード利用日を周期の参考にできます。その場合も元の書類日・参照明細番号を保持します。推定や複数返金の純額割当から請求日を勝手に置き換えません。

当月の同サービス書類があるのに未一致の場合は「書類あり・照合要確認」等と表示し、未提出と断定しません。過去書類の再アップロードだけでは当月の提出としません。解析できない当月書類がある場合は、不足か解析問題かを確認する表示です。

候補は `CardStatementItem.submitter_candidates` に、生成時点・根拠・参照先とともに保存します。**候補生成は `matched_user`、`matched_receipt`、金額計算、consume/reference台帳を変更しません。** 前月証拠を今月の証拠へ複製せず、未一致の状態を維持します。メールの自動送信や候補者への自動催促も行いません。書類が追加されれば次の再照合で候補を更新し、直接一致になった行の古い候補を消します。履歴が不足している場合は候補なしです。

画面では全候補を、照合結果PDFでは未確定の注記付きで上位3人を記載します。PDFは長い名前・ファイル名を省略表示し、詳細は画面を確認します。

## 実行環境・設定

Python 3.13／Django 5.2系。依存関係は `requirements.txt` を参照します。ローカルはSQLite、RailwayはPostgreSQLを想定しています。PostgreSQLのロック・並列動作はSQLiteだけでは検証できません。

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

環境変数の例は `.env.example` にあります。ただし本アプリ自体は `.env` ファイルを自動読込しません。シェルへexportするか、利用環境の変数設定・起動ツールから注入してください。

主な設定:

| 設定 | 用途 |
|---|---|
| `SECRET_KEY` | 本番で固有の安全な値を指定。Dockerビルド用値を使わない |
| `DEBUG` | 本番は `False` |
| `ALLOWED_HOSTS` / `CSRF_TRUSTED_ORIGINS` | 実際のドメイン／HTTPSオリジン |
| `DATABASE_URL` | PostgreSQL等への接続。未指定ならPGHOST等、どちらもなければSQLite |
| `RECEIPT_MEDIA_ROOT` | アップロード永続領域 |
| `RECEIPT_RETENTION_MONTHS` | ファイル保存期間。1～3か月 |
| `OPENAI_API_KEY` / `OPENAI_MODEL` | AI解析用の認証・利用可能なモデル |
| `RECEIPT_AI_FILENAME_ENABLED` | AI解析を使用する設定 |
| `RECEIPT_CARD_LAST4` | 管理する法人カード末尾 |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USERNAME` / `SMTP_PASSWORD` | SMTP接続 |
| `SMTP_FROM` / `APP_BASE_URL` | 差出人・メール内アプリURL |
| `TIME_ZONE` | 既定 `Asia/Tokyo` |

ローカルの初期作成例:

```bash
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

認証情報、`.env`、本番DB、ユーザーPDFはリポジトリへ含めないでください。

## Railwayのサービス設定

Web本体は `/railway.toml` を参照します。`predeploy.sh` が先にDjango checkを実行し、Web側でmigration、その後再checkを実行します。`start.sh` はGunicornを `0.0.0.0:$PORT` で起動します。`/health/` はDBクエリなしで応答します。Healthcheck成功だけでは全業務画面の動作保証にはなりません。

`receipt-reminder-*` は既定のpre-deploy分岐でmigrationをスキップします。`RECEIPTHUB_PREDEPLOY_MIGRATIONS=auto/true/false` で制御します。これは送信コマンドの設定とは別です。

| サービス／用途 | 設定ファイル | 実行コマンド |
|---|---|---|
| Web | `/railway.toml` | `/app/start.sh` |
| 毎月4日固定 | `/railway-email-reminder-4.toml` | `python manage.py send_receipt_reminders --kind initial` |
| 毎月10日固定 | `/railway-email-reminder-10.toml` | `python manage.py send_receipt_reminders --kind urgent` |
| 管理画面の送信日に追従する別方式 | `/railway-email-reminder-daily.toml` | `python manage.py send_receipt_reminders --kind auto` |
| 保存期限ファイルの定期削除 | `/railway-cron.toml` | `python manage.py purge_expired_receipts --noinput` |

固定4日＋10日方式と、毎日1回auto方式を重複して有効にしないでください。毎日autoでは管理画面に保存された日と今日が一致したときだけ送信します。送信しなかった過去日を自動追送する機能はありません。送信日・本文の保存だけでRailwayの定期実行設定は変わりません。

リマインダーにWeb用設定を使うとGunicornが常駐して終了しません。送信処理は終了するコマンドとして設定し、各サービスへ同じDB・必要なSMTP設定を渡してください。`Run now` や `--kind initial/urgent` は本送信し得ます。候補数だけを確認する例:

```bash
python manage.py send_receipt_reminders --kind initial --dry-run
python manage.py send_receipt_reminders --kind urgent --dry-run
```

メールの `--month` と `RECEIPT_REMINDER_TARGET_MONTH_OFFSET` は内部提出サイクルを指定します。通常offset=0です。通常リマインダーは必須領収書未確認者、重要リマインダーはそれにAPI確認待ちを含めます。管理者・停止アカウントは対象外です。テストメール成功は別Workerの起動・変数設定まで証明しません。既存コマンドは個別送信失敗を警告表示して終了するため、成功／失敗件数とEmailDeliveryLogを確認してください。このリリースではメール処理を変更していません。

## 保存期限・監査

保存期限の削除対象は物理ファイルです。抽出済みメタデータや使用履歴は引き続き参照します。領収書削除時の履歴スナップショットと明細削除時の消費解放は従来どおりです。単にファイルが期限切れになったことを理由に、過去の金額消費を再使用可能と扱わないでください。

Djangoの `django.request` と `receipts` のERRORは標準エラーへ出力します。500の調査はWebの実行ログでTracebackを確認します。本番で `DEBUG=True` に変更する必要はありません。ログには例外メッセージ内の個人情報等が含まれることがあるため、共有前に確認してください。

本リリースの作成環境では純Pythonテスト86件、構文・URL定義契約・JS構文を検証しました。Django依存パッケージを取得できず、`manage.py check`、migration実行、Django統合テスト、PostgreSQLの並列ロック、Railway実環境の画面表示は未実行です。テストコードの同梱と実行済み結果は区別しています。

確認すべき受入条件は、8月利用／9月支払が8月で照合されること、誤った利用月のファイルを通さないこと、証拠なしで提出済み表示にならないこと、上部と下部の件数が揃うこと、前月候補の参照で使用済み台帳を増やさないこと、現在書類の追加後に候補が更新されることです。
